| D-041 | 2026-10-31 | Payments settled in Phase 6 (contract: `docs/API.md`; data: `docs/DATA_MODEL.md`; machine: `docs/STATE_MACHINES.md`). **Scope note:** `docs/PRD.md` defines FR-PAY-01…06 only; the status / retry / reversal / attempt-limit requirements came from the Phase 6 instruction, and no FR-PAY-07…10 IDs were invented. (a) A `Payment` is an *attempt* with `status` completed / failed / reversed; only `completed` rows count toward `amount_paid`, which is recomputed from the rows (`Σ completed`) on every change, never incremented. (b) The limit `PAYMENT_MAX_ATTEMPTS` (env/setting, default 3) is measured as **failed attempts since the last completed payment or admin reset** (`Invoice.failed_attempts`), so several successful part-payments never exhaust it. `attempt_number = failed_attempts + 1`; a retry (`retry_of`, unique) continues the same streak. At the limit the invoice gets `payment_needs_attention` and further attempts get 409 `max_attempts_reached`; the way out is an **admin reset with a reason** (audited), not a silent timeout. (c) Reversal is **admin-only** and needs a reason; staff record and retry. A reversal restores the balance and takes Paid back to Confirmed; it does not touch the attempt counter. (d) Payment rows and `PaymentEvent` are never edited or deleted (PATCH/PUT/DELETE → 405). (e) Overpayment is refused for every attempt, including failed ones. (f) Customers see their own payments with a reduced field set and never the attention flag. (g) Concurrency: the invoice row lock is taken first, the payment row second, everywhere; DB constraint `UNIQUE(retry_of)` is a second line of defence for retries. (h) Odoo payment mirroring stays cut (KICKOFF §9): `odoo_sync_status = skipped`, no Odoo call is made, `ODOO_ENABLED` is irrelevant to payments. |
| D-042 | 2026-10-31 | **Row locks lock only the row they mean to lock:** every `select_for_update()` that is combined with `select_related()` uses `of=("self",)`. Reason: on PostgreSQL the lock otherwise extends to the joined rows, which (a) is rejected outright for a nullable join (this broke every subscription transition on Postgres, Phase 3) and (b) makes `skip_locked` billing skip subscriptions that merely share a plan. **The test suite is only trusted when it passes on PostgreSQL**; sqlite ignores `FOR UPDATE`, so it cannot catch this class of bug or verify concurrency.
